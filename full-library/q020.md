# 第20问 开源软件如何实现盈利

## 编辑摘要（新增，非原文）

本问介绍支持与服务、云服务、广告、硬件、众筹捐赠、认证培训和混合模式等商业路径，比较各自的优缺点与适用场景，并讨论开放核心、双重许可及企业案例。

- 开源项目有哪些收入来源？
- 双重许可和开放核心有什么区别？

相对于引入开源获得的降本增效的好处，还有一些企业更加深入地考虑：如何通过开源软件来赚钱。这方面已经有了不少好的经验可供借鉴。另外，一个开源项目的长期健康运行，其开发、维护需要资金支持，也需要考虑商业化的路径。

### 20.1 开源软件实现盈利的主流模式

开源软件实现盈利的主流模式包括支持与服务（订阅）模式、软件及服务（SaaS）与托管服务模式、广告模式、开源硬件模式、众筹/捐赠模式、认证培训模式以及混合模式等。各种模式通过不同途径（如提供增值功能、技术支持、云服务、培训认证等）实现开源项目的商业变现。

（1）支持与服务（订阅）模式。在该模式下，软件本身开源免费，但厂商为企业用户提供收费的技术支持、维护、培训和定制服务。典型案例包括红帽、SUSE、Canonica（Ubuntu）等开源操作系统厂商。以红帽为例，其企业版Linux（Red Hat Enterprise Linux）开源代码对外公开，但公司通过销售订阅服务（包括软件更新、补丁、SLA 级别支持等）获得收入。同样，Hortonworks（开源Hadoop供应商）、Percona（开源数据库供应商）等也依赖专业咨询和支持服务获利。此外，一些公司将源码免费发布给社区使用，企业若要求稳定运行或使用特定功能，就需购买技术支持。例如，MongoDB 提供免费社区版，但企业版订阅包含管理工具和专业服务。

（2）软件即服务（SaaS）与托管服务模式。该模式通过将开源软件以云服务形式提供给客户来盈利。厂商不直接售卖软件，而是通过订阅云平台或托管服务收费，典型例子有GitLab（GitLab 的托管服务），WordPress（Automattic 运营的托管版WordPress）以及数据库领域的MongoDB Atlas。MongoDB 的财报显示，Atlas 云服务收入占总收入的比例很大。例如，2022 财年第四季度，Atlas 收入同比增长85%，占当季58%的总收入。通过按需云部署、自动运维和按月付费，企业用户可以避免自行运维复杂系统，而厂商则获得持续的订阅收入。另外，一些开源项目将SaaS 模式与本地部署并行，用户可自行下载部署，也可选择购买托管服务。例如，Elastic 提供Elasticsearch 的云服务Elastic Cloud，Confluent 提供Kafka 的云平台等。SaaS 模式往往与开放核心结合，免费版可自建部署，但若想使用云托管或企业版，则需付费。

（3）广告模式。部分开源项目通过广告获得收入。例如，广告屏蔽插件AdBlock Plus 的源代码开源，但它允许谷歌等投放“可接受广告”并收取费用。此外，开源社区平台SourceForge 曾通过在其网站投放横幅广告获取大量收益（2006年单季收入曾达650 万美元，2009 年全年达到2300 万美元）。类似地，一些开源浏览器（如火狐Mozilla 浏览器）的收益也部分来自搜索引擎的广告分成。总体而言，广告模式多用于具备大流量用户基础的开源项目，但需注意保持社区信任、避免用户反感。

（4）开源硬件模式。将开源理念应用到硬件领域。厂商公开硬件设计图纸，使他人可自由制造衍生产品，但通过销售实体硬件或授权获利。代表性案例如Arduino：其单片机开发板设计完全开源，任何人可根据协议制造并销售Arduino硬件。Arduino 创始人主要通过销售标有Arduino 商标的官方产品获利：任何用Arduino 商标销售的板卡都需支付授权费用。这种模式下，开源硬件厂商靠销售实体产品（板卡、套件）、提供培训或技术支持获得收入，同时依靠品牌商标维护产品质量与形象。


<!-- source: q020; print_pages: 76; pdf_pages: 94–94 -->

（5）众筹/捐赠模式。开源项目可以通过社区和用户的资助获得资金。一种是众筹，即在Kickstarter、Indiegogo 等平台预售或收集开发基金。例如，开发者在Indiegogo 上为Mesa 图形库新增OpenGL 功能筹得2500 美元，还有开源游戏《大灾变：黑暗之日》（Cataclysm: Dark Days Ahead）通过Kickstarter 为全职开发者筹款实现长期开发。另一种是定期赞助或捐赠：项目在平台（如GitHub Sponsors、Open Collective、Patreon）上接受支持者的捐款。例如，Mozilla 基金会曾在《纽约时报》上刊登募资广告，为Firefox 1.0 版本募集启动资金。2019 年，GitHub 推出Sponsors 项目，国内的Gitee 也推出了类似的功能，使个人和公司能直接赞助其托管的开源项目。这些模式依赖社区支持，适用于具备热心用户和公益属性的项目，但可持续性和金额往往不稳定，需要结合其他模式共同使用。

（6）认证培训模式。开源项目衍生的培训和认证课程也是重要的收入来源。许多机构针对流行开源技术提供收费培训课程和认证考试，如红帽的RHCE/RHCSA认证考试、Linux 基金会的Kubernetes 认证（CKA/CKAD）等。企业用户或个人为获得官方认证或系统性培训往往愿意付费，而认证项目既增强了生态影响力，又带来了可观收入。此外，一些开源项目的官方培训与认证由第三方（如培训机构）承办，项目方通过授权或分成获益。

（7）混合模式。混合模式是指开源软件商业模式中结合开源许可证与专有许可证的方式，其核心思想是通过不同的许可证（或其他法律文书）构筑企业知识产权架构，并在此基础上获得合理的销售收入。常见的做法包括双重许可、开放核心、插件与增值功能或其他限制性许可模式，详见20.3 节。

### 20.3 开源商业的混合模式

常见的混合模式中，最古老也最成熟的一种是双重许可模式。这种模式是在开源许可的基础上，同时提供专有许可版本，或在免费核心版本上附加商业功能。用户可选择使用免费版进行评估或开发，若要在大规模生产或闭源环境中使用，则需要购买商业许可。经典案例是MySQL：Oracle 将MySQL 同时以GNU 通用公共许可证和商业许可证发行，商业许可证为那些无法接受GPL 约束的企业客户提供授权。类似地，SugarCRM、MongoDB（已改用SSPL）和Redis Labs（对某些模块采用商业闭源）等，都采用这种模式。

另一种广为采用的模式是开放核心模式。它与双重许可模式不同，通常将核心功能开源，在商业版中提供额外的企业功能或插件。例如，GitLab 既有开放源代码的社区版，又有收费的企业版（含更多CI/CD、高级安全等功能）。这种模式一方面扩大了产品的开源社区影响力，另一方面通过差异化功能和支持收取费用。

与开放核心模式非常相似，但更强调模块化和生态的是插件与增值功能模式。这种模式下的软件设计通常更精良，插件化架构方便用户像在“应用市场”一样挑选所需功能。像WordPress、Eclipse、Visual Studio Code、Firefox、Chrome 等软件都内置了这样的扩展市场。关键区别在于，这些插件或增值功能来源更广泛，既有开源的免费插件，也有由其他公司开发的商业插件，并不局限于软件原厂商提供。这能极大地促进软件生态繁荣和快速发展，但也可能导致发展方向超出原厂商控制。例如，Visual Studio Code 就限制其分支版本使用官方插件市场，以防范基于自身技术成长起来的强大竞争对手对自身市场的影响。


<!-- source: q020; print_pages: 78; pdf_pages: 96–96 -->

此外，还有一些公司尝试采用带有其他限制的许可模式，例如，SSPL、Commons

Clause 或BSL 等“源代码可用（Source Available）”，但不完全符合OSI 开源定义的许可证。这类许可通常保留代码可见性，但限制特定用途（如禁止大型云服务商将其直接作为托管服务盈利）。这更像是一种防御性策略，旨在保护自身收益不被云巨头侵蚀，而非成熟的商业模式。然而，这类策略往往效果不佳，既易引发社区强烈反对，又难以实现商业目标。例如，Redis Labs 曾添加 Commons Clause 限制销售，后因社区反对而撤回；MariaDB 的MaxScale 也经历了从GPL 改为商业源许可，3 年后又改回GPL 的反复。事实证明，这种改变许可证的策略往往得不偿失。

### 20.4 各类混合模式的商业动机与技术考量

近年来，混合模式与多元化策略成为趋势。一方面，更多的厂商选择通过开源基金会对开源项目进行长期持续的支持；另一方面，开源项目与社区也在不断创新，GitHub Sponsors、Open Collective、Patreon 等平台帮助个人开发者获得持续收入，一些项目还在尝试通过区块链代币经济或开源孵化器获得资金支持（仍处于早期）。总体趋势是各种模式互补并用，根据项目特点灵活组合以提高可持续性。

（1）吸引用户与社区规模：开源核心模式鼓励用户免费试用并参与社区，从而迅速扩大用户基础并获得口碑。这有利于提高产品成熟度和促进社区贡献。例如，Oracle MySQL 通过GPL 免费版吸引开发者，然后向大规模部署或商业用途收取费用。技术上需将商业功能与开源核心分离，可采用插件架构或许可校验机制，确保用户能清晰区分免费/付费功能范围。

（2）研发投入回报：许多公司投入大量研发成本，开源方式虽然扩大了影响力，但需要商业模式支撑持续创新。商业授权或专有模块收入可回流研发。例如，Elastic、MongoDB、Confluent 等强调，它们对开源项目投入巨资，而变更许可证或销售企业版是保证继续投资的手段。技术考量上，这要求项目维护者在保留核心价值的同时，区分开源部分与企业部分，经常使用许可证标记、构建脚本或分支管理等方式。

（3）应对云服务商竞争：近年来，云厂商经常以开源项目为基础提供托管服务，抢占市场份额且对原厂回馈有限。为保护自身利益，一些公司采用限制性许可证（如SSPL、Commons Clause 许可证、Confluent 许可证等），要求将其软件用作SaaS 服务的厂商必须开源其整套服务代码。Elastic 的CTO 直言“我们的许可证变更旨在阻止他人直接将我们的产品作为服务提供”。技术上，这涉及在许可证中明确禁止特定用途，以及在产品中加入许可验证或水印。虽然能限制云厂商无偿占用其软件，但会被社区质疑其不再真正开放。

混合模式的选择应结合产品类型和公司阶段。早期创业公司或初创产品，常倾向于保持更纯粹的开源（以获取社区和客户），成长后可逐步引入混合元素；高技术壁垒的企业软件适合采用开源+商业扩展，而依赖规模服务盈利的产品（如云数据库、企业搜索等）则可能更早尝试许可证创新或SaaS 模式。各种模式均需平衡“社区贡献”和“商业收益”两个目标，混合模式的优势在于提高灵活性和可持续性，劣势则在于可能引发社区信任危机和法律合规压力。选择适合自身的模式，谨慎规划许可证和商业策略，对开源公司持续发展至关重要。
